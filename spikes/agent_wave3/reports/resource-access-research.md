# FUI-008: Darwin native resource access research

- Read-only investigation on 2026-11-18; only this report was written. No production changes, dependencies, servers, policy changes, destructive race tests, or database investigation.
- Actual host: `Darwin 27.3.0`, `arm64`, kernel `xnu-13432.60.57~99/RELEASE_ARM64_T6000`; `sw_vers`: macOS `27.3`, build `26C5035r`. Commands: `uname -a`, `sw_vers`.

| `O_NOFOLLOW_ANY` | `0x20000000` | Reject symlinks anywhere in the supplied pathname. Darwin-full feature namespace. Not a directory-rename lock. [L2,L3] |
| `O_RESOLVE_BENEATH` | `0x00001000` | `openat` pathname resolution must not escape its starting directory. This is a real public Darwin flag here, not Linux `openat2`. [L2,L3,S1,S2] |

| `O_BENEATH`, `openat2` | Not found | Neither appeared in the installed public include-tree search; `clang -dM` on `<fcntl.h>` emits the flags above, not `O_BENEATH`. Do not invent either Darwin interface. [L2; local inspection] |

## The essential distinction: object capability versus current pathname

1. **Pinned object capability:** an open fd identifies the opened object despite later replacement of its old pathname. `fstat(fd)` describes that object; reading/writing the fd does not reopen the string. This is useful replacement protection. [L3,L5,S2]
2. **Strict current-path containment:** at the instant of every read/write/create, the object and effective parent must still belong to the currently authorized root hierarchy. A retained fd and preflight canonicalization do not establish this stronger property. [L3,L4,S2,S3; inference from the interfaces]
3. Counterexample for a component walker: open `root/a` as `a_fd` using `O_DIRECTORY|O_NOFOLLOW`; another actor renames `root/a` to `outside/a`; then `openat(a_fd, "file", ...)` or `openat(a_fd, "new", O_CREAT|O_EXCL|O_NOFOLLOW, ...)` still uses the moved directory object. There need be no symlink or `..`. A later `read`/`write` of an already-open child likewise has no root-fd argument. **Walking alone does not prevent ancestor relocation.** [L3,L5,S2; semantic counterexample, not an executed host race]
4. Adding `O_RESOLVE_BENEATH` to the final `openat(a_fd, ...)` confines that lookup relative to **a_fd**, not the original project root. Opening the complete relative path from the original root in one syscall is preferable, but does not confer permanent containment on the returned fd. [L3,S2,S3]
5. In public XNU, `NAMEI_RESOLVE_BENEATH` rejects absolute starts, absolute symlink targets, and `..` when the current vnode is the starting vnode; the inspected uses are lookup controls, not an ongoing ancestry guard on fd I/O. `FMASK` does not persist `O_RESOLVE_BENEATH` as a read/write constraint. Do not extrapolate Linux rename-race guarantees or claim that this source proves arbitrary concurrent ancestor-renames safe even during one Darwin lookup. [S1–S3]
6. `realpath`, `F_GETPATH`, `ATTR_CMN_FULLPATH`, parent-chain checks, and pre/post identity checks can detect some changes; another rename can occur after the last check. Detecting a bad write afterward cannot undo its unauthorized side effect. They are evidence/diagnostics, **not an authorization fence**. Advisory file locks are also not a hostile directory-renamer exclusion primitive. [L4,L6,L7; inference]

**Acceptance implication:** do not label a descriptor-walking implementation “SEC-10 complete” if SEC-10 means strict current-path containment under an external actor's ancestor renames. Explicitly decide which contract is intended; under the stronger contract, unavailable enforcement must return an unsupported/denied result before I/O, not silently downgrade to object-capability semantics.

## Public atomic facilities and sandbox/helper possibilities

- `openat(root_fd, complete_relative_path, O_RESOLVE_BENEATH|O_NOFOLLOW_ANY|O_CLOEXEC|access, ...)` is an implementable public native lookup/open building block on this host. It rejects escaping traversal and links in that lookup; it is **not** an atomic “check ancestry and read/write forever” facility. No such general public fd-root-bound read/write primitive was identified in the inspected APIs. [L2,L3,S1–S3]
- `O_CREAT|O_EXCL|O_NOFOLLOW` atomically rejects an already-existing final entry, including a dangling symlink. Add `O_NOFOLLOW_ANY|O_RESOLVE_BENEATH` and perform creation using the original root fd and full relative path, rather than a canonicalized absolute string. This addresses final-entry substitution, **not** the moved-parent/current-containment problem. [L3,S2]
- `O_TRUNC` takes effect during open: never use it before establishing the required authorization/identity contract. Opening without truncation, checking the actual fd, then using `ftruncate` protects identity selection but still does not make ancestry-plus-mutation atomic. Same warning applies to creating first and validating its parent afterward. [L3,L5; inference]
- Darwin also has syscall-specific nofollow/beneath controls (e.g. `renameatx_np` in public XNU); names/flags must be verified for each intended operation. Atomic namespace publication is not a general ancestry freeze, and plain `renameat` must not inherit `openat` guarantees by analogy. [S4]
- Supported Apple direction: **App Sandbox**, signed least-privilege helper/XPC service and user-selected-folder security scope. Apple's docs describe recursive grants and passing scoped bookmarks to another process. This can add kernel policy enforcement, but its broad default allowances and grant/revocation/rename semantics must be checked against the exact per-root requirement; the cited docs do **not** promise the strict concurrent-rename property above. [A1–A3]
- `sandbox-exec` still has a public manpage but is explicitly **deprecated**; `sandbox_init` is “No longer supported,” its public header reserves flags except `SANDBOX_NAMED`, and recommends App Sandbox. Custom Seatbelt policy syntax is not a supported stable public containment API established by these declarations. [L8,L9]
- A separate **trusted native helper with fixed typed operations and no fork/exec of requested commands** is a distinct research candidate from wave1's arbitrary-process-tree cancellation runner. A deprecated `sandbox-exec` launcher could be evaluated only as an explicitly approved experiment, not presumed production approval. A helper alone provides process separation, not filesystem containment; require deny-by-default policy, minimal inherited handles, verified operation-time enforcement and rename tests, and a documented support/deployment story before making any containment claim. [A1–A3,L8,L9; recommendation]
- Kernel MAC hooks exist on vnode reads/writes, which is an architectural enforcement point; the open-source hooks do not disclose/prove Seatbelt's complete policy implementation or eliminate policy-check-to-use races. Do not claim a sandbox solves the strong contract without evidence for that policy on the supported OS/filesystems. [S2]
- If strict containment is mandatory and no verified policy/primitive prevents or correctly mediates relocation, **fail closed**. An application mutex, `NSFileCoordinator`, prechecks, or a watcher cannot constrain an uncooperative external renamer. A separately controlled filesystem tree could change the threat model, but requires proving other writers cannot rename its ancestors; do not change permissions or add privileged infrastructure as an implicit FUI-008 implementation. [L4,S2,S3; engineering conclusion]

## Root identity, aliases, overlap, and unavailable volumes

- For a currently mounted filesystem, compare opened objects by `(st_dev, st_ino)` from `fstat`, using the native 64-bit inode ABI. `ATTR_CMN_DEVID` corresponds to `st_dev`; `ATTR_CMN_FILEID` corresponds to `st_ino`. This is a **live-object/mount identity**, not a durable authorization token across reboot, deletion/recreation, or remount. [L5,L6]
- For persistent hints use supported volume UUID plus file ID/capability information, not path spelling alone. `ATTR_VOL_UUID` identifies the volume; `ATTR_CMN_FSID` matches `statfs.f_fsid`; deprecated `ATTR_CMN_OBJID` must not be assumed equal to `FILEID`. Check valid capability masks and filesystem support; persistence is filesystem-dependent. Reopen and verify identity on use/re-enrollment; a stored identifier never grants access by itself. [L6,L10]
- Case/Unicode spellings: ask the filesystem to resolve names and compare object identities; never lowercase paths as a universal identity rule. Check `VOL_CAP_FMT_CASE_SENSITIVE`, `CASE_PRESERVING`, and object-ID capabilities. Same-object roots are equivalent regardless of alternate spelling; do not grant both independently. [L6,L10]
- Hard links are not symlinks: a regular file can have an in-root and an outside name for the same object. Define whether authorization covers entries or forbids externally aliased objects. This SDK additionally documents `O_UNIQUE` (reject multiple hard links at open); it is not an enduring uniqueness/ancestry guarantee, so `st_nlink` prechecks alone must not be advertised as that guarantee. [L2,L3,S1,S2]
- Symlink root enrollment must be explicit: either reject symlinks throughout the supplied root path, or resolve the user-selected root and pin/record the actual target identity. Later retargeting the original symlink must not authorize its new target. Enrollment-time canonical path is display/discovery data, not a reusable safe access path. Treat firmlink views/mount aliases as OS-resolved identity issues too. [L3–L6; recommendation]
- Overlap API should report `Equivalent`, `Ancestor`, `Descendant`, `Disjoint`, or **`Indeterminate`**. Equality uses live identities; ancestry can use descriptor/identity parent traversal or resolved ancestry evidence, with mount boundaries and concurrent changes tracked. A race makes that traversal a snapshot, not an enduring lock. For exclusion decisions, `Indeterminate` must conservatively block; do not infer disjointness from string-prefix failure or inaccessible parents. Recheck policy generation before actual access. [L3,L5,L6; recommendation]
- A path beneath a root can cross a mount without containing a symlink. These open flags are not a public `NO_XDEV`/network ban. Define whether nested volumes/network filesystems are allowed; inspect actual fd filesystem/volume metadata. A post-create volume check is too late to prevent an unauthorized creation, so deny unsupported creation scenarios if volume policy cannot be enforced before effects. [L2,L6,L11; recommendation]
- Ordinary active file references can make unmount return `EBUSY`; `O_EVTONLY` deliberately does not prevent unmount. `MNT_FORCE` can unmount active files; subsequent accesses error even after remount. An old fd must never be treated as automatically revived against a new mount at the same path. [L3,L12]
- Use `fstat`/`fstatfs` and actual syscall results for stale/unavailable handling; preserve raw errno and typed errors (`EIO`, `ENXIO`, `ESTALE`, `EBADF`, missing path, denied access). Do not promise one universal “volume vanished” errno or a preflight that predicts every later read. Successful metadata does not prove subsequent availability or containment; zero-byte EOF is distinct from an error. [L5,L11–L13]

## Implementable native Rust boundary (proposal, not implementation)

- `RootHandle`: private `OwnedFd`, verified identity/volume metadata, policy generation and declared enforcement capability (`PinnedObject` vs `StrictCurrentContainment`). Never expose an “authorized absolute path” as the security result. [L3,L5; design]
- Typed `RelativePath` rejects absolute paths, NUL, `..`, unsupported namespace forms, and ambiguous inputs. Deny child symlinks initially; use complete relative paths from `RootHandle` with native flags. Supporting symlinks later needs an explicit target policy and race proof, not `realpath` followed by ordinary open. [L2,L3,S3; design]
- Internal `open_existing`, bounded `read`, `enumerate`, `create_new`, and edit operations consume the same root/policy state. Check actual opened type/identity, reject devices/FIFOs/unsupported objects, avoid blocking special-file opens, and do not export raw handles that bypass revocation. Search/index consumers receive only authorized bytes/entries with policy generation; revocation must cancel/drop outstanding work and suppress stale results. No arbitrary command-runner API. [L3,L5; design satisfying SEC-11]
- `create_new` uses `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW|O_NOFOLLOW_ANY|O_RESOLVE_BENEATH|O_CLOEXEC`, restrictive creation mode, and actual fd identity. Existing-file edit opens without `O_TRUNC`; separate explicitly supported replacement semantics from in-place fd writes. These are safe building blocks **only within the declared enforcement contract**. [L2,L3; design]
- Feature-bind to SDK declarations (or a small audited FFI shim if Rust bindings lag), verify behavior on every supported OS baseline/filesystem, and fail closed on missing/ignored semantics. Current probes do not establish first introduction versions. Do not retry insecurely without a flag on `EINVAL`/`ENOTSUP`. [L2,L3; design]
- **Must fail closed:** strong containment requested without verified enforcement; root identity mismatch/replacement; stale/unavailable mount; unsupported volume identity or mutation semantics; unresolved root alias/overlap; symlink/escape input; unsupported special object; revoked policy; creation whose effective-parent containment cannot be guaranteed. Return specific errors, not an empty authorized result. [requirements; conclusions above]

## Implementation observations added after the read-only research

- Native probes on this host showed `open('/private', O_DIRECTORY | O_NOFOLLOW_ANY)` succeeds, but combining `O_NOFOLLOW_ANY` with `O_NOFOLLOW` returns `EINVAL`. The implementation uses the stricter whole-path flag alone; this is a corrected flag combination, not a retry without protection. Creation recipes above are conceptual and must not be copied with that invalid combination.
- The local `getattrlist.2` error section (lines 1949–1952) requires the volume root when requesting volume attributes. The implementation uses `fstatfs` to locate the mount, opens its directory, checks the device against the selected descriptor, and queries its UUID there. Neither the mount path nor a persisted UUID is treated as an authorization grant.
- The user explicitly chose strict current-location containment during implementation. The current native module implements root metadata and denial of unsupported content operations, not a pinned-object content access fallback. Positive read/create remains blocked pending proof of the stronger contract.

Later explicit product decision: the user replaced continuous-location containment with validation per operation and deferred signing/distribution. The current implementation now opens validated objects with beneath/nofollow controls and retains that object through the operation. This is a declared contract change, not proof that the original stronger contract was implemented; see [OPERATION-IO.md](../OPERATION-IO.md).
