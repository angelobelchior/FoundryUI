# FUI-003 / FUI-004 — Windows and Linux isolation research

## Status and evidence boundary

Documentary research, 2026-11-18; only Microsoft, Docker, Linux kernel and bubblewrap project sources inform the technical claims below. Inputs: `FoundryUI-Specs/tickets/FUI-003-prova-isolamento-windows.md`, `FUI-004-prova-isolamento-linux.md` and `03-permissoes-isolamento-e-rede.md` (SEC-09/10/14–17 and NET-01–05).

**This report ran no confinement tests.** Environment supplied by the coordinating session: macOS 27.3 arm64 host; an available Docker daemon running Linux aarch64 and an existing native AzureLinux ARM64 image; no native Windows environment. These are supplied environment facts, not independently collected measurements. A Linux container result there would concern that Linux daemon/kernel/image configuration, not native macOS containment or universal Linux desktop support. Docker documents that Desktop bind mounts cross a Linux VM boundary and that mounts are resolved by the daemon, not the client.[L2]

Windows x64 and ARM64 remain **not proven**. Native Linux desktop x64/ARM64, rootless Docker and bubblewrap remain **not proven by this report**. Python-stdlib prototype launchers, command construction tests and fail-closed checks are useful harness evidence, but do not by themselves establish an OS security boundary. Do not mark either ticket accepted from documentary evidence.

## Windows: documented mechanisms and limits

| Area | Documentary evidence | Consequence for the spike (recommendation, not a tested guarantee) |
|---|---|---|
| AppContainer launch | Microsoft explicitly supports launching an unpackaged Win32 AppContainer using a profile/package SID, `SECURITY_CAPABILITIES`, `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`, `STARTUPINFOEX` and `CreateProcess` with `EXTENDED_STARTUPINFO_PRESENT`. AppContainer access combines user/group and AppContainer grants: the effective permission is their intersection.[W1] | Prefer this as the Windows candidate over an ordinary subprocess. A profile alone is not enough: verify the launched token and effective access. Omit network capabilities; do not copy the documentation's illustrative `internetClient` grant. |
| Files and grants | Regular AppContainers have some system-file/registry/COM access; LPAC opts out of `ALL APPLICATION PACKAGES` access and needs additional capabilities. AppContainers also have profile storage.[W1] DACL updates require ownership or `WRITE_DAC`; inheritable ACEs can propagate to existing children.[W2] | “Nothing outside the project is accessible” is too broad. Explicitly inventory runtime/profile exceptions and authorized user-data roots; evaluate LPAC compatibility. Grant the specific SID only required rights on controlled fixtures/staging, not broad user directories or `ALL APPLICATION PACKAGES`. Record and clean up grant/profile lifetime without overwriting concurrent ACL changes. |
| Network | Microsoft says an AppContainer without network capability cannot access the network.[W1] Separately, Windows exposes a configured list of AppContainer SIDs permitted to send loopback traffic for debugging.[W3] | Test IPv4/IPv6, LAN, DNS, loopback and UNC/SMB on the actual build; inspect exceptions without changing unrelated machine policy. Also test named pipes/COM/services as indirect brokers: network capability absence alone does not demonstrate the product's complete “no indirect network” policy. |
| Creation hygiene | `CreateProcessW` otherwise uses the caller's security context; a null environment inherits the parent's environment. Inherited handles retain their access rights; an explicit handle list is available. `lpCurrentDirectory` merely selects the initial directory and can even be UNC.[W4] | Use an explicit executable path, a minimal Unicode environment, and tightly scoped stdio handle inheritance. Exclude credentials/tokens/SSH-agent endpoints, not just proxy variables. Confirm a denied file cannot be accessed through a leaked inherited handle. |
| Descendants and kill | `CreateProcess` children normally join the parent's Job Object. Breakaway flags alter this; Microsoft's documented `Win32_Process.Create` exception creates processes outside the job. `TerminateJobObject` targets associated processes; `KILL_ON_JOB_CLOSE` works when the **last** job handle closes. Job Objects are not a replacement for per-process security restrictions.[W5] | Keep breakaway disabled and the job handle non-inheritable. Combine AppContainer access restrictions with Job lifecycle control; explicitly deny/test WMI/service-mediated execution rather than assuming genealogy catches it. Test launcher crash and handle leaks as well as explicit cancellation. |

### Why restricted token / working directory is insufficient

`CreateRestrictedToken` removes privileges, makes SIDs deny-only and/or adds restricting SIDs checked against object DACLs. This is a useful access-control primitive, but selecting “restricted” does not automatically define approved filesystem roots, network policy or descendant lifecycle. Microsoft also warns about restricted applications interacting with unrestricted applications on the default desktop.[W6] Therefore a restricted-token-only launcher is **not evidence** of SEC-14/15 confinement. Likewise, initial working directory does not change object access rights or deny absolute paths.[W4] Canonicalizing a string once cannot satisfy the spec's access-time identity requirement.

Recommended launch ordering: establish profile/grants and hardened startup attributes; create suspended; assign to a configured Job Object; resume only after successful assignment. `CREATE_SUSPENDED` prevents the primary thread from running until resumed.[W7] Any failure must terminate the suspended process and return unavailable, not retry unsandboxed. This sequence needs native tests; it is not an implemented result of this research.

### Windows distribution implications

The documented AppContainer route uses Windows APIs rather than a Docker dependency and supports a caller-chosen moniker for a directly launched Win32 process; it does not require pretending the desktop app is UWP.[W1] Package any native helper and its dependencies for each supported architecture and document supported Windows builds, ACL-capable storage assumptions and ordinary-user grant permissions.[W1][W2]

Windows 11 ARM supports x86/x64 user-mode emulation; Windows 10 ARM supports x86 only. Emulation does not cover kernel drivers, which must be ARM64. Microsoft recommends `IsWow64Process2` to distinguish native and emulated execution.[W8] Consequently an x64 run under emulation is not a native ARM64 helper test. For a `ctypes` prototype, validate structure sizes, pointer-width declarations and error paths on both targets; distribution of Python is a separate prototype dependency, not the production sandbox design.

## Linux: Docker candidate versus native bubblewrap

| Area | Documentary evidence and resulting recommendation |
|---|---|
| `--network none` | Docker creates only loopback, with no configured IPv6 loopback address in its documented example.[L1] This establishes the intended network namespace configuration, **not** absence of every IPC path. Test direct IPv4/IPv6/DNS/LAN/host access independently; do not equate one failed HTTP request with policy proof. |
| Bind mounts | Bind mounts expose daemon-host files and are writable by default; `readonly` prevents filesystem writes. Existing submounts are included by default; recursive read-only requires kernel 5.12+, otherwise submounts can remain writable.[L2] Prefer an explicit minimal `--mount`, private propagation, and deliberate submount policy. A writable project is a real host mutation grant, not a disposable copy. Test mount-source substitution and symlink races rather than assuming a precomputed canonical path fixes them. |
| Sockets and brokers | Docker warns that daemon control can mount and alter the host filesystem; the daemon is rootful unless rootless is explicitly selected.[L3] bubblewrap explicitly warns that a bound D-Bus socket can execute commands through systemd.[L6] Do not expose Docker/Podman sockets, SSH agents, D-Bus, arbitrary `/run`, home directories or host IPC. A project may itself contain a socket: mounting only that project is not automatically safe. Read-only mount status is not a broker authorization policy. Test a controlled Unix-socket relay, including a socket introduced after launch. |
| Rootless Docker | Both daemon and containers run in a user namespace without host root; this differs from `userns-remap`, whose daemon remains root. Requirements include `newuidmap`/`newgidmap` and subordinate UID/GID ranges.[L4] A non-root container user or an ARM64 daemon does **not** establish rootless mode. Record actual daemon security options/context/endpoint and UID mapping. Rootless still grants the daemon the invoking user's authority and adds daemon installation/lifecycle/storage dependencies. |
| Resource limits and cancellation | In rootless Docker, cgroup run flags require cgroup v2 and systemd; Docker says flags are ignored if those conditions are absent.[L5] Linux cgroup v2 documents inherited membership, `cgroup.kill` for the whole subtree including concurrent forks, and `cgroup.events: populated` for live-process presence.[L8] Verify effective controllers/delegation and limits, not merely accepted CLI arguments. `docker kill` documents signalling the container's main process, not the local Docker CLI; shell-form entrypoints may not forward signals.[L9] Use container identity for cancellation and observe stopped state plus delayed-write sentinels. |
| bubblewrap | Upstream describes a policy-construction tool, **not a complete sandbox**. It always creates a mount namespace; user/PID/network/IPC isolation and visible mounts depend on arguments. Current upstream relies on unprivileged user namespaces and removed historical setuid mode.[L6] It avoids a Docker daemon/image dependency, but needs a maintained helper, kernel/distro namespace availability, a tested runtime filesystem and explicit policy. |
| bubblewrap lifecycle/policy | Upstream documents `--unshare-net`, `--unshare-pid`, `--clearenv`, `--new-session`, `--die-with-parent`, read-only binds and externally supplied seccomp filters. `--unshare-all` includes best-effort `*-try` options; a cgroup namespace is not resource-limit setup.[L7][L8] Require mandatory features explicitly; never accept silent degradation or `--not-a-security-boundary`. Use separately verified cgroup lifecycle/limits where required. `--die-with-parent` is a candidate to test, not a reason to skip descendant/adversarial cancellation tests. |

Linux kernel documentation explicitly discusses concurrent renames, symlinks, mount traversal and `openat2` resolution restrictions.[L10] Application `realpath`/prefix checks are therefore not sufficient access-time authorization for trusted host-side tools. Minimal namespaces/mounts reduce exposed resources but do not remove the need to test hardlinks, concurrent replacement, inherited descriptors and broker entry points. A cgroup manages processes/resources; it does not itself impose a filesystem allowlist.[L3][L8]

## Recommendation and outstanding actual-proof gate

1. **Windows:** retain AppContainer/LPAC + minimal grants/environment/handles + non-breakaway Job Object as the candidate. Keep command actions unavailable until native tests pass independently on Windows x64 and ARM64. Do not substitute restricted token, working directory or a mocked API test as proof.
2. **Linux Wave1:** use the available native ARM64 AzureLinux image only for bounded, reproducible Docker experiments. Pin/report the local image ID/digest, daemon/kernel versions and architecture; do not pull/install implicitly. Harden with no network, minimal mounts, dropped capabilities, no-new-privileges, read-only runtime and verified resource limits. These are proposed controls, not security guarantees. Evaluate rootless Docker and native bubblewrap separately before choosing desktop distribution; neither inherits proof from a rootful VM-backed daemon.
3. **Required matrix:** per OS/build/architecture/backend, demonstrate authorized reads/writes work and unauthorized ones fail; `..`, absolute/case/UNC paths, symlink/junction/hardlink and concurrent replacement probes; direct and brokered network/IPC denial; credential/descriptor inheritance reduction; composed scripts and detached grandchildren; cancellation/launcher crash followed by a delayed-write observation window. Include ordinary-user permissions, unsupported filesystem/kernel/policy configurations and deliberate setup failures.
4. **Fail closed:** missing helper/API/image/daemon, unverified grants/controllers, setup failure, unsupported platform or inconclusive cleanup must return unavailable/uncertain. Never run the original command without containment. Retain the writer/resource exclusion until termination and absence of further effects are established; termination is not rollback of earlier writes or externally queued work. Keep mediated HTTP outside the untrusted process under separate authorization/audit controls, as required by the specs.
